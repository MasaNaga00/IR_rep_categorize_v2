## 1. 目的と範囲

### 1.1 目的

カメラ等の修理データ(ユーザコメント・修理者コメント)を LLM で分類し、修理ごとに次の情報を出力する(仕様メモ第14.5節)。

- ユーザが申告した故障内容
- 申告のうち、修理者が確認できたもの
- 修理者が確認した故障内容
- メーカー責任修理を含むか(YES/NO)
- 代表故障

### 1.2 作業の分担と情報の流れ

| 範囲 | 担当 | 場所 |
|---|---|---|
| 要件定義、架空データ、テスト、ロジック実装、Dify 呼び出し部、評価スクリプト、プロンプト初版、YAML 初版、手順書 | Claude | Mac(実データなし) |
| 環境構築、Dify ワークフロー構築、実データでの実行、正解データ作成、精度評価、プロンプト調整、YAML の内容調整 | GPT(ユーザの指示による) | Windows(実データあり) |

## 3. 全体の流れ

```
[入力CSV]
  ↓ (1) 読み込み・列の対応づけ             input_loader
  ↓ (2) 故障数・番号の存在の計算            failure_count
  ↓ (3) 製品ごとにバッチ化して Dify 呼び出し   llm_request / dify_client
[層1: 生出力 JSON]
  ↓ (4) パース・検証・エラー時の再試行       llm_response
  ↓ (5) 中間データの作成(引き継ぎ・空の行)  tables
[層2: 中間データ 4表]
  ↓ (6) 判断ルールの適用                    judge
[層3: 最終出力(修理単位)]
  ↓ (7) ファイル出力・実行メタ情報           outputs
```

- R-14: 実行の入口は `python -m repclass.run`(第9節)。

## 4. 分類コード体系(YAML)の拡張

### 4.1 製品セクション

- R-15: 各製品セクション(`product_categories.<製品ID>`)と各故障コードに、次のキーを持たせる。

**製品セクション**

| キー | 必須 | 内容 |
|---|---|---|
| `name` | 必須 | 表示名(例: ミラーレスカメラ)。既存 |
| `code_prefix` | 必須 | コードの接頭文字(例: `M`)。製品間で重複不可 |
| `failure_categories` | 必須 | 故障コード一式。既存 |
| `environment_factors_override` | 任意 | 環境要因の追加・上書き(4.3) |

**故障コード**

| キー | 必須 | 内容 |
|---|---|---|
| `name` | 必須 | 既存 |
| `description` | 必須 | 既存 |
| `record_type` | 必須 | `failure` / `service` / `unknown`。既存 |
| `responsibility` | 必須 | `manufacturer` / `user_or_unknown`。2026-11-01 に全コード設定済み |
| `role` | 任意 | 特別な役割: `connected_device`(接続機器要因)/ `other`(その他)/ `unknown`(判定不能) |

- 既存の ML / LENS には、次の値を追加する。
  - `code_prefix`: ML は `M`、LENS は `L`
  - `role`: M047 / L037 = `connected_device`、M046 / L036 = `other`、M_UNK / L_UNK = `unknown`
- `meta.version` を `0.3.0` にする。

### 4.2 自動チェック(仕様メモ第16.5節)

- R-16: `load_codebook()` は次をチェックし、1つでも違反があれば `CodebookError` を送出する。メッセージには違反をすべて列挙する。
  1. 必須キーがそろっている(R-15)
  2. 各製品に、`role` が `connected_device`・`other`・`unknown` のコードが1つずつある
  3. 各製品に、`record_type: service` のコードが1つ以上ある
  4. 全コードの `responsibility` が `manufacturer` か `user_or_unknown`
  5. `code_prefix` が製品間で重複していない
  6. 各コードが自製品の `code_prefix` で始まる
  7. 環境要因のキーが重複していない。`always_user_caused` は真偽値
- 同じチェックを、コマンド `python -m repclass.check_codebook [--codebook <path>]` でも実行できるようにする。Windows 側で YAML を調整した後の確認に使う。

### 4.3 環境要因

- R-17: 既存のトップレベル `environment_factors` を、全製品共通の既定値とする。各要因に次のキーを追加する。
  - `always_user_caused`: `true` の要因は、LLM の判定に関係なく常にユーザ起因とする。既定値は `false`。
  - `impact`(落下・衝撃)と `water`(水濡れ・浸水、雨を含む)に `true` を設定する(2026-11-02 確定、Q3 案A)。
- R-18: `none` と `unknown` は LLM の出力では使わない。環境要因が無ければ空の配列で表す。
- R-19: 製品の `environment_factors_override` で、要因の追加(新しいキー)や、既存要因のキーの上書きができる。

### 4.4 ユーザ申告再現の値

- R-20: 新しいトップレベル `claim_reproduction_statuses` を追加する。既存の `reproduction_statuses` は旧方式用(v2 リポジトリでは削除済み)。

| 値 | 表示名 | 「確認できた」に含む |
|---|---|---|
| `reproduced` | 再現 | はい |
| `partial` | 一部再現 | はい |
| `not_reproduced` | 再現せず | いいえ |
| `not_mentioned` | 記載なし | いいえ |
| `out_of_scope` | 対象外 | いいえ |
| `request_only` | 依頼のみ | いいえ |

- 各値に `name`(表示名)、`description`、`counts_as_confirmed`(真偽値)を持たせる。
- 判定の指示は第7.2節(R-31)に書く。

### 4.5 API

- R-21: `repclass.codebook` は次を提供する。

```python
def load_codebook(path: str | Path) -> Codebook: ...

class Codebook:
    version: str                 # meta.version
    sha256: str                  # YAML ファイルのハッシュ値(実行メタ情報用)
    def product_ids(self) -> list[str]: ...
    def code(self, product_id: str, code: str) -> CodeInfo | None: ...
    def is_valid_code(self, product_id: str, code: str) -> bool: ...
    def is_manufacturer(self, product_id: str, code: str) -> bool:   # 未定義コードは False
    def is_service(self, product_id: str, code: str) -> bool: ...
    def code_by_role(self, product_id: str, role: str) -> str: ...
    def environment_factors(self, product_id: str) -> dict[str, EnvFactorInfo]: ...  # 既定値 + 上書き
    def claim_statuses(self) -> dict[str, ClaimStatusInfo]: ...
    def code_list_text(self, product_id: str) -> str: ...   # LLM に渡すコード一覧(4.6)
```

### 4.6 LLM に渡すコード一覧

- R-22: `code_list_text()` は、その製品の全コードを1行1コードで出力する。
  - 各行の形式は `コード | 名称 | 説明文`。
  - responsibility は含めない(LLM に責任を判断させないため)。

### 5.1 修理者コメントの注記の除去(2026-11-08 追加)

修理者コメントの後ろには、修理とは関係のない注記(ファームウエアの更新、シャッター回数、バッテリーの劣化、別の機器の所見など)が、決まったマークの後に書かれることがある。LLM がこれを故障や追加の発見と読まないよう、Dify に渡す前に Python で取り除く。

- R-64: 取り除くマークは設定ファイル `comment_preprocess.yaml` の `note_markers` で指定する(ローカル作業フォルダ → リポジトリの `config/` の順で探す。R-05a)。
  - マークは1文字以上の文字列。YAML では `"\u25FE"` のように `\u` の形で書くことを推奨する(エディタや文字コードの違いで化けないため)。
  - 比べるときは、絵文字の見た目を変える見えない文字(U+FE0E、U+FE0F)を無視する。そのため `◾️` と `◾` は同じマークとして扱う。
  - 初期値は ◾(U+25FE)、⭐(U+2B50)、※(U+203B)、■(U+25A0)、★(U+2605)。実データの文字は Windows 側で確認して設定する(Mac では実データの文字を確認できないため)。
  - `note_markers` が空なら何も取り除かない。
- R-65: 取り除く範囲は、マークから「次のマーク・次の丸数字(①〜⑳)・コメントの終わり」のうち最初に来るところの手前まで。丸数字で止めるのは、注記の後に番号付きの修理内容が続く場合に、それを消さないため(2026-11-08 ユーザ了承。これにより、マークごとに扱いを分ける必要はない)。
- R-66: 対象は修理者コメント。ユーザコメントにかけるかどうかは `apply_to.user_comment` で選べる(既定: かけない)。内部コメントにはかけない。
- R-67: 取り除いた文は捨てない。
  - `repairs.csv` の `repair_comment` / `user_comment` は入力どおりの全文とし、取り除いた文を `repair_comment_notes` / `user_comment_notes` に ` | ` 区切りで出力する。
  - Dify に渡すのは取り除いた後の文(R-30)。抜き出しの確認(R-34 `excerpt_not_found`)は、取り除いた後の文と入力どおりの全文のどちらに含まれていてもよい。
  - 実行フォルダに `removed_notes.csv`(列: row_number、excel_row、repair_id、field、removed、remaining。取り除いた文と、取り除いた後の文)を出力する。dry-run でも出力する(Windows 側でマークの設定を確かめるため)。
  - `run_meta.json` に、使った設定ファイルのパス・sha256・マーク(`U+25FE` の形)・注記を取り除いた修理の件数を記録する。実行時の要約(dry-run を含む)に、注記を取り除いた修理の件数とマークを表示する。マークが設定されているのに1件も取り除かれなかった場合は、マークの文字が実データと合っていない可能性がある旨を表示する。

## 6. 故障数(Python)

- R-27: `count_failures(user_comment: str) -> FailureCountResult` を提供する。
  - `failure_count`: ユーザコメント中の丸数字(①〜⑳)の最大値。丸数字が無ければ 1。
  - `present_numbers`: ユーザコメントに出現した番号の集合
  - `missing_numbers`: 1〜`failure_count` のうち、出現しない番号(番号飛び)
- R-28: ユーザコメントが空欄でも、`failure_count` は 1 とする。

## 7. LLM の入出力

### 7.1 リクエスト

- R-29: バッチは**製品ごと**に作る(1つのバッチに複数の製品を混ぜない)。既定のバッチサイズは 10 修理。
- R-30: Dify ワークフローへの入力変数は次の3つ。
  - `product_name`: 製品の表示名
  - `code_list`: `code_list_text()` の出力
  - `records`: 次の要素の JSON 配列(文字列にして渡す)

```json
{"repair_id": "R001", "failure_count": 2, "missing_numbers": [],
 "user_comment": "...", "repair_comment": "..."}
```

- `user_comment` / `repair_comment` は、注記を取り除いた後の文(R-64〜R-67)。
- プロンプト本文は `config/prompts/v2/system_prompt.md` で管理し、Dify に貼り付ける。判断ルールはプロンプトに固定し、コード一覧だけを変数で渡す(仕様メモ第16.2節)。

### 7.2 プロンプトに含める判断の指示

- R-31: プロンプト初版には、次の判断の指示と、それぞれの短い架空の例を含める。

**ユーザ申告再現(reproduction)**
- 判定はキーワードではなく、文の意味で行う。
- 修理者がその番号について、原因・所見・処置を書いている場合は `reproduced` とする。「再現した」と明記されていなくてもよい。
  - 例: 「hogeにより起こっていました」「○○を交換」
- 「繰り返し確認したが再現しませんでした」「症状確認できず」「異常は認められませんでした」など、症状を確認できなかった記述は `not_reproduced` とする。二重否定などの回りくどい言い回しも含む。
- 条件付きで再現した場合、または一部の症状だけ再現した場合は `partial` とする。
- その番号について再現の有無が読み取れない場合は `not_mentioned` とする。
- 「レンズ側で対応」のように、別の機器や対象外の扱いとされた場合は `out_of_scope` とする。
- 点検・清掃などの依頼で、不具合の訴えがない場合は `request_only` とする。
- ユーザコメント側に「ご指摘外の現象」として書かれたもの(`【ご指摘外の現象】` の表記を含む)は、修理者が見つけた故障なので `reproduced` とする(2026-11-02 確定、Q2)。
- 「予防交換」は、修理者コメントに処置として書かれていても `not_reproduced` とする(2026-11-02 追記)。
- 「関連箇所を点検いたしましたが、異常はございませんでした。」のような定型文は `not_reproduced` の根拠とする。

**前置きと【】(2026-11-02 追記)**
- 丸数字の前の前置きも読む。
  - 例: 修理者コメントの「ショック品」は環境要因(落下・衝撃、記述は修理者)
  - 例: 「メンテナンスで入庫しましたが、修理に移行しました」は、依頼のみではなく通常の申告として扱う
- `【修理上限金額：100000円】` のような事務的な【】は無視する。
- `部品【基板ユニット】を交換` のような【】は、部品名として読む。
- `【オーバーホール】①…②…` のような前置きの【】は、入庫の目的として読む。故障数は丸数字で決まる(R-27)。

**レンズのゴミ・汚れ・キズ(2026-11-03 追記)**
- 前玉・後玉など、レンズの外側の表面のゴミ・汚れ・キズ(拭き取りで除去できたものを含む)は「レンズ表面:ゴミ/汚れ/キズ」(L039、responsibility は `user_or_unknown`)。
- 分解が必要なレンズ内部のものは「レンズ内:ゴミ/キズ/汚れ」(L028、メーカー責任)。
- 内部か表面か判断できない場合は L039(表面・ユーザ責任)に倒す。カメラのセンサーゴミ(M012 / M013)と同じ考え方。

**現象を確認できなかった場合(2026-11-03 追記)**
- 修理者が「ご指摘の現象は確認できませんでした」と書いている場合は、その後にカメラ内部のエラー履歴・推定・部品交換が書かれていても `not_reproduced` とする。エラー履歴や推定での部品交換は、修理者の手元で現象を確認したことにならない。
- 例外: ユーザから提出された画像・動画・撮影データなどの証左で、修理者が現象を確認できた場合は `reproduced` とする(現品で再現しなかった場合も含む)。
- 考え方: メーカー責任修理として集計するのは、現象を確認できた修理だけとする(推定で部品を交換していても、現象を確認できていなければ NO)。
- 背景: 実データで、「確認できませんでしたが、エラー履歴より…部品を交換」という修理が「再現」と判定され、誤って YES になっていた。

**設定・操作が原因の場合(2026-11-03 追記)**
- カメラ・レンズの設定や操作が原因で現象が発生しており、部品の不具合が無い場合は、`reproduced` とし、修理者視点コードを「設定・操作起因」(ML: M048、LENS: L038。responsibility は `user_or_unknown`)にする。「動作不良」「その他」にしない。
- その後に続く「設定を解除後動作点検いたしましたが、異常はございませんでした」は、設定を直した後の確認結果なので `not_reproduced` の根拠にしない。
- 背景: 実データで、設定が原因の修理が「動作不良」「その他」(どちらもメーカー責任)に分類され、誤って YES になっていた。

**修理者が書いた部位・原因のコード(2026-11-08 第2弾 追記)**
- 確認できた行の修理者視点コードは、修理者が不具合の部位・原因を書いている場合、その部位・原因に合うコードにする。ユーザが訴えた現象のコードをそのまま使わない。
  - 例: 「電源スイッチ部の不具合により…交換」→ 電源SW不具合(M021)。電源不良(M001)にしない
  - 例: 「AF-ONボタン部のゴム欠損…【カバーユニット（バック）】を交換」→ 背面操作部不具合(M026)。その他(M046)にしない。M026 / D028 の説明文に、AF-ONボタン・マルチコントローラーと、ボタン類のゴム・カバーの破損・外れを含めた(YAML 0.5.1)
- 修理者が部位・原因を書かず、現象の確認と処置(製品交換など)だけを書いている場合は、現象に合うコードにする。
- まとめ書き(「①②同じ部品の不良」)の扱い(下の「修理者視点コード」)の例外: 修理者が書いた部位・原因に直接対応するコードがある場合は、各行の修理者視点コードをそのコードにする。対応するコードが無い部位(DC/DCコンバータ、温度センサー、基板など)は、今までどおりその行自身のユーザ視点コード。
- 背景: 実データで、「①②電源スイッチ部の不具合により」の①が電源不良になっていた(まとめ書きのルールで、①のユーザ視点コードがそのまま入ったと推測)。

**メモリーカードが原因の場合(2026-11-08 第2弾 追記)**
- 修理者が、預かったメモリーカード側が原因で本体に異常が無いと書いている場合は、メディア不具合(M011、メーカー責任)にしない。
  - カードの使い方(空き容量不足、フォーマットの推奨など)が原因 → `reproduced` / 設定・操作起因(M048)
  - カード自体の不良 → `reproduced` / 接続機器要因(M047)
- 背景: 実データで、SD カードの空き容量不足で動作が遅くなっていた修理が、メディア不具合(メーカー責任)になっていた。

**ユーザ視点コードの選び方(2026-11-08 第2弾 追記)**
- コメントに出てくる言葉ではなく、起きている現象でコードを選ぶ。例: スイッチを操作していないのに AF/MF の表示が切り替わる → スイッチの不具合(L006)ではなく動作不良(L042、2026-11-08 追加、メーカー責任)。L006 の説明文を「スイッチそのものの不具合」に限定した。
- ユーザが電源スイッチ・ボタンなどの操作部材そのものの操作に触れている番号は、その操作部材のコード。現象だけを書いている番号は、現象のコード。例: ①「電源を切ろうとしても切れない」→ M001 / ②「電源スイッチを OFF にして押さえている間は切れるが、離すとまた入る」→ M021。

**充電器・バッテリーが原因の場合(2026-11-13 追記)**
- 修理者が、充電器・バッテリー側が原因と書いている場合は、次のコードにする(ML / DC。LENS には無い)。

| 原因 | コード(ML / DC) | responsibility |
|---|---|---|
| 純正の充電器の不良(バッテリーチャージャー、純正の USB 電源アダプターを含む) | 充電器不良 M051 / D051 | `user_or_unknown`(2026-11-14 変更。それまでは `manufacturer`) |
| 純正のバッテリーの不良(内部回路の不良、膨らみなど) | バッテリー不良 M052 / D052 | `user_or_unknown`(2026-11-14 変更。それまでは `manufacturer`) |
| バッテリーの劣化・寿命(長期間の使用による容量の低下、買い替えのお勧めなど) | バッテリー劣化(寿命) M053 / D053 | `user_or_unknown` |
| 他社製・互換品のバッテリー・充電器、USB 充電に使う汎用の充電器・ケーブル・モバイルバッテリー | 接続機器要因 M047 / D046 | `user_or_unknown` |

- 純正か他社製かが書かれていない場合は、純正とみなす。「他社製」「互換」「サードパーティ」「汎用の USB 充電器」などと書かれている場合だけ接続機器要因にする。
- 充電器・バッテリーは付属品なので、純正品の不良でもメーカー責任のカウントから外す(2026-11-14 ユーザ決定。2026-11-13 の決定ではメーカー責任としていた)。充電器・バッテリーだけが原因の修理は NO になり、代表故障は空になる。カメラ本体の不具合も同時にあれば、そちらで YES になる。
- 純正品の不良・劣化・他社製を分けてコードを付けるのは、発生状況を把握するため(責任区分はどれもユーザ責任)。
- ユーザ視点コード: ユーザが充電器・バッテリーそのものの不具合に触れている番号は、そのコード。現象だけ(「充電できない」など)の番号は、現象のコード。
- 修理者コメントの後ろの注記(「⭐️バッテリーが劣化しております」など)は、Dify に渡す前に取り除く(R-64〜R-67)ので、このコードにはならない。このコードが付くのは、充電器・バッテリーがユーザの申告の原因だった場合だけ。
- 背景: これまでは純正品の不良も接続機器要因(ユーザ責任)に分類されていた。

**製品実力の範囲内の場合(2026-11-08 追記)**
- 修理者が「製品実力の範囲内」「規格内」「仕様の範囲内」「製品仕様によるもの」など、製品の実力・規格・仕様の範囲内と書いている番号は、`reproduced` とし、修理者視点コードを「製品実力範囲内」(ML: M049、LENS: L040、DC: D049。responsibility は `user_or_unknown`、record_type は `failure`)にする。
- その後に調整・部品交換が書かれていても(規格より厳しい範囲での顧客対応として行ったもの)、不具合のコードにしない。
- `reproduced` とする理由: 現象(同一機種との差異など)は確認できているため。repair_code がユーザ責任のコードなので、YES/NO は NO になる。
- 背景: 実データで、「製品実力の範囲内ではございますが、同一機種と比較して差異があることを確認いたしました。可能な限り関連箇所を調整いたしました。」がメーカー責任(ズーム自重落下)になっていた。

**外から触れる部分の汚れ(2026-11-08 追記)**
- ディスプレイオフセンサー(アイセンサー)、カメラ・レンズの電気接点など、外から簡単に触れられる部分の汚れが原因で現象が発生し、清掃・拭き取りだけで解消した場合は、`reproduced` とし、修理者視点コードを「外部の汚れ(清掃で解消)」(ML: M050、LENS: L041、DC: D050。responsibility は `user_or_unknown`)にする。表示の不具合・通信エラーなどのコードにしない。
- 分解が必要な内部の汚れ、部品交換を行ったもの、清掃しても解消しなかったものは含めない。撮像センサー表面のゴミ(M013)、ファインダー表面(M015)、レンズ表面(L039 / D010)は、それぞれのコードを使う。
- 考え方: 容易に拭き取れる汚れは、ユーザの使用中に付いたものとみなす(2026-11-08 ユーザ決定)。
- 背景: 実データで、「ディスプレイオフセンサー部の汚れによりご指摘の現象が発生したため、関連部の点検清掃を実施いたしました」が LCD 表示不具合(メーカー責任)になっていた。

**付随作業(2026-11-02 追記)**
- 「※作業に伴いカメラ設定を初期化しました」「※最新ファームウエアに更新しました」のような、修理に付随して行った作業は**処置とみなさない**。修理者視点コードをファームアップ(サービスコード)にしない。
- ファームウエアの更新**そのもの**で症状が改善したと書かれている場合だけ、ファームアップのコードにする。

**同原因(basis)**
- 「②は①と同じ原因」のように他の番号を参照している場合は、`basis` を `same_cause` とし、`ref_sub_id` に参照先の番号を入れる。

**修理者視点コード(repair_code)**
- 修理者が特定した実際の不具合のコードを入れる。
- 確認できなかった行は、次のとおりとする(2026-11-02 確定)。
  - `not_reproduced`・`not_mentioned`: 空(`null`)
  - `request_only`: 行った作業のサービスコード(例: 清掃なら M043)
  - `out_of_scope`: `role` が `connected_device` のコード(接続機器が原因でこの製品に異常がない場合)
- 「①②同じ部品の不良」のようなまとめ書きは、「同原因」と同じ扱いとし、各行の修理者視点コードはその行自身のユーザ視点コードとする(2026-11-02 確定、R-43 と同じ考え方)。ただし、修理者が書いた部位・原因に直接対応するコードがある場合は、そのコードにする(2026-11-08 第2弾、上の「修理者が書いた部位・原因のコード」)。
  - LLM には各行を `direct` で出力させ、`repair_code` に各行のユーザ視点コードを入れるよう指示する。

**ユーザ視点コード(user_code、2026-11-02 確定)**
- 依頼のみの行は、依頼の内容のコードとする(例: 清掃依頼なら M043、オーバーホール依頼ならオーバーホールのコード)。
- ユーザコメントが空欄の場合は、`role` が `unknown` のコード(判定不能)とする。

**環境要因**
- 記述があるものだけを出力する。
- 通常では考えづらい使用かどうかを `abnormal_use` に入れる。
- その環境に実際にさらされた・その取り扱いが実際にあったと書かれているものだけを出力する(2026-11-08 追記)。
  - 「雨に当たらないよう気をつけていた」「落としたことはない」「防湿庫で保管していた」のような、否定している文や気をつけていたという文は環境要因にしない。
  - ただし、修理者が水濡れ痕・腐食・衝撃痕など、その環境にさらされた跡を確認している場合は、ユーザが否定していても環境要因とする(source は `repair`。2026-11-08 ユーザ決定)。
  - 背景: 実データで、「なるべく雨に当たらないよう丁寧に扱っており」の「雨」から水濡れ(常にユーザ起因)と判定され、誤って NO になっていた。

**抜き出し(excerpt)**
- 原文からそのまま抜き出す。要約や言い換えはしない。

### 7.3 期待する LLM 出力(1修理あたり)

- R-32: LLM は次の形の JSON を返す。全体は `{"results": [ ... ]}` とする。確信度(confidence)は出力させない(2026-11-02 確定、Q4)。

```json
{
  "repair_id": "R001",
  "claims": [
    {
      "sub_id": 1,
      "user_excerpt": "電源が入らない",
      "user_code": "M001",
      "reproduction": "reproduced",
      "basis": "direct",
      "ref_sub_id": null,
      "repair_code": "M001",
      "repair_excerpt": "電源基板不良"
    }
  ],
  "environment": [
    {"factor": "impact", "source": "user", "abnormal_use": true, "excerpt": "落としてしまった"}
  ],
  "extra_findings": [
    {"description": "別途グリップラバー劣化", "repair_code": "M028", "excerpt": "グリップラバー劣化あり"}
  ]
}
```

| 項目 | 値 |
|---|---|
| `basis` | `direct`(直接確認)/ `same_cause`(他の番号と同原因)/ `none`(根拠なし) |
| `ref_sub_id` | `basis` が `same_cause` のときの参照先の番号。それ以外は `null` |
| `source` | `user` / `repair` / `both` |
| `abnormal_use` | 通常では考えづらい使用か(真偽値) |

### 7.4 検証

- R-33: `parse_llm_response(raw: str | dict) -> ParsedBatch` は、次のいずれの形でも受け付ける。
  - `{"results": [...]}`
  - 配列そのもの
  - コードブロック(```json)で囲まれた JSON 文字列
- R-34: `validate_result(result, request_record, product_id, codebook) -> list[ValidationIssue]` は、次の項目をチェックする。各問題には `repair_id`、`sub_id`、種類、メッセージを持たせる。

| 種類 | 内容 | 扱い |
|---|---|---|
| `count_mismatch` | `claims` の件数が `failure_count` と違う | エラー |
| `sub_id_invalid` | `sub_id` が 1〜`failure_count` の範囲外、または重複している | エラー |
| `unknown_code` | コードがその製品のコード体系にない | エラー |
| `invalid_enum` | `reproduction`、`basis`、`source`、`factor` が定義外の値 | エラー |
| `ref_invalid` | `same_cause` なのに `ref_sub_id` が無い・自分自身・範囲外 | エラー |
| `missing_repair` | 結果に含まれない `repair_id` がある | エラー |
| `parse_error` | 応答が JSON として読めない | エラー(バッチ内の全修理) |
| `api_error` | Dify の呼び出しに失敗した(R-47 のリトライ後) | エラー(バッチ内の全修理) |
| `excerpt_not_found` | 抜き出しが原文に含まれない(空白の違いは無視する。注記を取り除く前・後のどちらの文に含まれていてもよい。R-67) | 警告 |
| `ref_cycle` | 同原因の参照が循環している | 警告 |

### 7.5 エラー時の動作

- R-35: エラーが出ても処理は止めず、**最終出力まで作る**。
- R-36: エラーのあった修理は、自動で1回だけ再試行する。
  - 再試行は、その修理だけを1件ずつ送る形で行う。
  - 再試行でもエラーが残った修理は `status = error` とする。
- R-37: 修理の状態(`status`)は次の3つ。
  - `ok`: 問題なし
  - `warning`: 警告のみ。判断結果は出力する
  - `error`: エラー
    - 判断結果の列(`manufacturer_repair`、`representative_code` など)は**空欄**にする。`NO` とは区別する。
    - `error_reason` に、エラーの種類を入れる。
- R-38: `status = error` の修理も、`final.csv` と `repairs.csv` に1行として出力する。どの修理がエラーかを一覧で分かるようにするためである。
- R-39: エラーの修理の入力を `error_repairs.json` に出力する。
- R-40: `--resume <timestamp>` を指定すると、前回の実行でエラーだった修理だけを再実行する。
  - 結果は新しい実行フォルダに出力する。
  - 前回の `ok` / `warning` の結果と結合して、**全件そろった最終出力**を作る。
  - `run_meta.json` には、再実行元の timestamp を記録する。

### 8.1 中間データ(仕様メモ第14.4節)

- R-41: `build_tables(requests, parsed_results, codebook) -> Tables` は、次の4つの表を作る。各表は dict のリストとして持つ。

| 表 | 列 |
|---|---|

### 8.2 Python 側で機械的に適用するルール
