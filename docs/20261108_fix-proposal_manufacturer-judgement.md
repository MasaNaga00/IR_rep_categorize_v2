## 1. 例1: 雨に気をつけていたのに、水濡れ(ユーザ起因)になる

### 原因(確認済み + 推測)
- 確認済み: YAML で `water` は `always_user_caused: true`。LLM が environment に water を1つでも出すと、修理全体が必ず NO になる(R-44、R-47)。
- 確認済み: プロンプト第6節は「コメントに使用環境・取り扱いの記述があるものだけを出力する」としか書いていない。**否定の文や、気をつけていたという文の扱いが書かれていない。**
- 推測: LLM が「なるべく雨に当たらないよう丁寧に扱っており」の「雨」を、水濡れの記述と読んだ。

### 修正案
プロンプト第6節に、次の指示と架空の例を足す。Python は変えない。

```
- 環境要因は、その環境に実際にさらされた・その取り扱いが実際にあったと書かれているものだけを出力する。
  - 「雨に当たらないよう気をつけていた」「落としたことはない」「水には濡らしていない」「防湿庫で保管していた」のように、
    否定している文や、気をつけていたという文は環境要因にしない。
  - 例: ユーザ「雨の日は使わないようにしており、使用後は防湿庫で保管していた。レンズ内に汚れがある」→ environment は空
  - 例: ユーザ「小雨の中で撮影した後から曇りが出た」→ water(source: user)
- 修理者が「水濡れ痕」「腐食」など、水にさらされた跡を確認している場合は、ユーザが否定していても water(source: repair)とする。
```

- 最後の行は、ユーザが否定していても修理者が痕跡を見つけた場合に、正しく NO にするための指示。**この扱いでよいか、確認をお願いします(質問1)。**

### この修正で残る点(推測)
- この例は、修理者コメントの内容によって L028(レンズ内、メーカー責任)などになり、YES になる見込み。

## 2. 例2: 「製品実力の範囲内」

### 原因(確認済み)
- 「製品実力」を表すコードが無い。調整や部品交換が書かれていると、LLM は不具合のコード(この例ならズーム自重落下 L009、メーカー責任)を選ぶ。

### 修正案
**(1) 各製品に新しいコードを追加する**(YAML 0.5.0)

| 製品 | コード | 名称(案) | record_type | responsibility |
|---|---|---|---|---|
| ML | M049 | 製品実力範囲内 | failure | user_or_unknown |
| LENS | L040 | 製品実力範囲内 | failure | user_or_unknown |
| DC | D049 | 製品実力範囲内 | failure | user_or_unknown |

- 説明文(案): 「修理者が『製品実力の範囲内』と判断したもの。規格より厳しい基準での差異で、顧客対応として調整・部品交換を行った場合も含む。メーカー責任の範囲外とみなす。」
- record_type は、Tableau で「不具合」として数えるか「作業」として数えるかに関わる。案は failure(現象自体はあったため)。**service にしたい場合は教えてください(質問2)。**

**(2) プロンプトに指示を足す**(第5節、「設定・操作が原因の場合」と同じ形)

```
- 製品実力の範囲内の場合: 修理者が「製品実力の範囲内」と書いている番号は、reproduction を "reproduced"、
  repair_code を「製品実力範囲内」のコードにする。その後に調整・部品交換が書かれていても、不具合のコードにしない。
  - 例: ユーザ「ズームリングが勝手に伸びる」/ 修理者「製品実力の範囲内ではございますが、同一機種と比較して差異があることを確認いたしました。関連箇所を調整いたしました。」
    → reproduced / 製品実力範囲内
```

- reproduction を "reproduced" にする理由: 現象(同一機種との差異)は確認できているため。repair_code がユーザ責任のコードなので NO になる。代表故障は空。
- **どの言い回しを「製品実力」として扱うか**は業務の判断なので、確認をお願いします(質問3)。例: 「製品実力の範囲内」だけか、「規格内」「仕様の範囲内」「製品仕様によるもの」も含めるか。

## 3. 例3・例4: 後付けの注記と「追加の発見」

### 3.1 M001・M046 はどこで追加されたか(コードで確認済み)

`src/repclass/judge.py` で、`repair_confirmed_codes` は次の2つをつないで作っている(R-46、Q1 の決定)。

1. 確認できた行(再現・一部再現)の `repair_code`
2. **`extra_findings`(修理者側だけの発見)の `repair_code`**

claims.csv の repair_code は M013 だけなので、**M001・M046 は extra_findings から来ている**(コードから判断。実データの extra_findings.csv は見ていないので、念のため確認をお願いします)。

- 例3: 「⭐️バッテリーが劣化しております」を LLM が追加の発見と読み、M001(電源不良)を付けた(推測)。
- 例4: 「◾️レンズの防滴マウントゴムが破れている」を追加の発見と読み、合うコードが無いため M046(その他、メーカー責任)を付けた(推測)。
- どちらも M013 はユーザ責任なので、M001・M046 が付いたことで **YES になっていた**可能性が高い(推測)。

### 3.2 修正案A: 後付けの注記を、LLM に渡す前に Python で取り除く

**動き**
- 修理者コメントの中で、決まったマーク(◾️・⭐️・※ など)から始まる部分を取り除いてから Dify に渡す。
- 取り除く範囲は「マークから、次のマーク・次の丸数字(①〜⑳)・コメントの終わりのどれか最初に来るところまで」。丸数字で止めるのは、注記の後にまだ番号付きの修理内容が続く場合に、それを消さないため。
- 取り除いた文は捨てずに、`repairs.csv` の新しい列 `repair_comment_notes` に残す(何を消したか後で確かめられるように)。
- 実行時の要約に「注記を取り除いた修理: N件」を表示する。dry-run でも分かるようにする。
- 内部コメントにはかけない。ユーザコメントにかけるかどうかは設定で選べるようにする(既定: かけない。「【ご指摘外の現象】」はマークではないので影響しない)。

**例3での動き(見込み)**
```
元:   センサー表面を清掃いたしました◾️カメラのファームウェアを最新のファームウェアに更新しました。◾️…◾️現在のシャッター回数は約1000回です。⭐️バッテリーが劣化しております。お買い替えをお勧めいたします。
渡す: センサー表面を清掃いたしました
```

**設定ファイル(新規 `config/comment_preprocess.yaml`、案)**
```yaml
# 修理者コメントから取り除く注記のマーク。ここから始まる部分を取り除く。
note_markers:
  - "◾"   # ◾ 黒い中くらいの小さい四角(Mac で見える ◾️)
  - "⭐"   # ⭐ 星(Mac で見える ⭐️)
  - "※"   # ※ 米印
  - "■"   # ■ 黒い四角(Windows・Shift-JIS で使われやすい)
  - "★"   # ★ 黒い星(同上)
apply_to:
  repair_comment: true
  user_comment: false
stop_at_circled_number: true
```
- 比べる前に、絵文字の見た目を変える見えない文字(U+FE0F など)は無視する。そのため「◾️」と「◾」は同じマークとして扱える。
- ローカル作業フォルダにこのファイルが無い場合は、リポジトリの `config/` の初期値を使う(R-05a の探す順と同じ)。**Windows 側で何もしなくても初期値で動く。**

**マークの文字が Windows で違う場合に、どこを調整するか**
- Mac で見えている ◾️ ⭐️ は、元のデータの文字と同じとは限らない。Excel・CSV の保存方法(特に Shift-JIS)によって、■(U+25A0)や★(U+2605)に置き換わっていたり、「?」に化けていたりすることがある。
- 調整する場所は **ローカル作業フォルダの `comment_preprocess.yaml` の `note_markers` だけ**。コード(`src/`)は変えない。
  1. リポジトリの `config/comment_preprocess.yaml` をローカル作業フォルダにコピーする(`init` でもコピーされるようにする)。
  2. 実データのマークの文字コードを Excel で調べる。例: マークが A2 の 15文字目なら `=UNICODE(MID(A2,15,1))` → 9632 なら U+25A0(■)、9733 なら U+2605(★)。
     - 10進数を16進数にするには `=DEC2HEX(9632)` → `25A0`。
  3. `note_markers` に `"■"` の形で足す。文字そのものではなく `\u` の形で書くと、エディタやファイルの文字コードの違いで化けない。
  4. `python repclass_cli.py run --input <CSV> --dry-run` を実行し、要約の「注記を取り除いた修理」の件数と、`repairs.csv` の `repair_comment_notes` 列を見て、意図どおり取れているか確かめる。
- 「?」に化けている場合は、CSV を「CSV UTF-8」で保存し直す(Shift-JIS の読み込みの問題 Q10 と同じ)。

**注意点(確認をお願いしたいこと、質問4)**
- ※ や ◾️ の後に、判断に必要な内容が書かれることはありますか。例: 「※落下痕あり」「◾️水濡れ痕を確認」。あると、取り除いたことで環境要因が消え、**NO が YES に変わる**おそれがある。
  - あまりない場合: 案のまま全部取り除く。
  - ある場合: マークごとに「取り除く / 残す」を分ける(例: ⭐️ は取り除き、※ は残す)などの対応を考える。

### 3.3 修正案B: 「追加の発見」を、YES/NO・代表故障の判断から外す

- ユーザの説明: 修理者が見つけた故障は、ユーザコメントに「ご指摘外の現象」として書かれるので、修理者コメントだけにある発見は判断に使わなくてよい。
- **R-46〜R-48 と Q1 の決定(2026-11-02)を変える**。
  - `repair_confirmed_codes`: 確認できた行の `repair_code` だけにする(extra_findings を足さない)。
  - YES/NO(R-47)と代表故障(R-48)も、確認できた行だけで決める。R-48 の手順2(extra_findings から代表故障を取る)は削除する。
- extra_findings の扱いは2案。**案 b1 を推奨**(質問5)。
  - b1: LLM には今までどおり出させ、`extra_findings.csv` と final.csv の参考の列(`extra_finding_codes`)に残す。判断には使わない。何を見つけていたかを後で確かめられる。
  - b2: LLM に出させない(プロンプトから第7節を削除し、出力が少し短くなる)。
- 修正案Bだけでも、例3・例4の M001・M046 は消える。修正案Aは、注記が claims の判断(再現・コード)に影響するのを防ぐためのもので、両方入れるのを推奨。

## 4. 例5: ディスプレイオフセンサーの汚れ

### 原因(推測)
- 「液晶画面が映らなくなった」+「点検清掃」で、LLM が LCD 表示不具合(M017、メーカー責任)を選んだと考えられる。外から触れる部分の汚れを表すコードが無い。

### 修正案
**(1) 新しいコードを追加する**(YAML 0.5.0)

| 製品 | コード | 名称(案) | responsibility |
|---|---|---|---|
| ML | M050 | 外部の汚れ(清掃で解消) | user_or_unknown |
| DC | D050 | 外部の汚れ(清掃で解消) | user_or_unknown |

- 説明文(案): 「ディスプレイオフセンサー(アイセンサー)など、外から簡単に触れられる部分の汚れが原因で現象が発生し、清掃だけで解消したもの。分解が必要な内部の汚れや、部品交換を行ったものは含めない。撮像センサー表面のゴミは M013、ファインダー表面のゴミは M015。」
- LENS に入れるかは、範囲によって決まる(下の質問6)。

**(2) プロンプトに指示を足す**(第5節)
```
- 外から触れる部分の汚れ: ディスプレイオフセンサー(アイセンサー)など、外から簡単に触れられる部分の汚れが原因で、
  清掃だけで解消した場合は、reproduction を "reproduced"、repair_code を「外部の汚れ(清掃で解消)」にする。
  現象が表示の不具合などでも、表示の不具合のコードにしない。
  - 例: ユーザ「背面モニターが急に表示されなくなった」/ 修理者「アイセンサー部の汚れにより現象が発生していたため、点検清掃を実施いたしました」
    → reproduced / 外部の汚れ(清掃で解消)
```

- **範囲を確認させてください(質問6)。** どちらにするかで、コード名と LENS への追加が変わります。
  - 狭い案: ディスプレイオフセンサーの汚れだけ。
  - 広い案: 外から触れる部分の汚れで、清掃だけで解消したもの全般(例: レンズ・カメラの電気接点の汚れによる通信エラーも含む)。広い案では、今メーカー責任になっている接点汚れの修理も NO になる。

## 5. 進め方(承認いただいた後の作業)

これまでの流れ(要件定義書 → テスト → 実装 → 文書)で進めます。

1. 要件定義書の変更: R-31(環境要因の否定・製品実力・外部の汚れ)、R-46〜R-48(追加の発見を外す)、新しい要件(注記の除去、R-64〜)、第11節の決定に追加
2. YAML 0.5.0: M049 / L040 / D049(製品実力)、M050 / D050(外部の汚れ)。changelog に理由
3. 新しい設定ファイル `config/comment_preprocess.yaml` と、`init` でのコピー
4. プロンプト: 第5節・第6節(・第7節)の指示と架空の例
5. 架空データ: 今回の5つの例を架空の文に言い換えたシナリオ(T046〜)と期待値を `tools/fixture_gen` で追加
6. テスト: 注記の除去(マークの種類、見えない文字、丸数字で止まる、列への保存)、判定の変更、新コードの責任区分
7. 実装: 注記の除去(input_loader または llm_request の前)、judge.py、要約の表示
8. 文書: 仕様メモの変更履歴、Windows 向け資料(ローカル作業フォルダに反映する内容、マークの調べ方)、テスト件数・架空データ件数
9. 全テスト、`check`、実 YAML で架空データを通す確認

**Windows 側で必要になること(見込み)**
- 新しい版に置き換え、テストを流す。
- ローカル作業フォルダの YAML に新コードを足す(codes-export → Excel で行を追加 → codes-import でもよい)。
- プロンプトを新しい版で置き換え、Dify に貼り直す。
- `comment_preprocess.yaml` のマークを実データの文字に合わせる(3.2)。
- dry-run → 少量で実行して、5つの例の型が直ったか確かめる。

## 6. 確認をお願いしたいこと

1. 例1: ユーザが「雨には当てていない」と書いていても、修理者が水濡れ痕・腐食を確認していれば水濡れ(ユーザ起因)としてよいか。
2. 例2: 製品実力のコードの record_type は failure(案)でよいか。service にするか。
3. 例2: 「製品実力」として扱う言い回しはどれか(「製品実力の範囲内」だけか、「規格内」「仕様の範囲内」なども含むか)。
4. 例3: ※ や ◾️ の後に、落下痕・水濡れ痕など判断に必要な内容が書かれることはあるか。マークごとに扱いを分ける必要はあるか。Windows で使われているマークの文字(■・★ など)が分かれば教えてほしい。
5. 例3・4: 追加の発見は、b1(CSV には残し、判断には使わない。推奨)か、b2(LLM に出させない)か。
6. 例5: 外部の汚れのコードは、ディスプレイオフセンサーだけ(狭い案)か、接点の汚れなども含める(広い案)か。
