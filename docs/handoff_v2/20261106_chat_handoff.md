## 1. プロジェクトの目的と概要

### 1.1 目的
品質保証業務で扱うカメラ等の修理データ(ユーザコメント・修理者コメント)を、LLM(Dify 経由)で分類し、修理ごとに次を出力して Tableau で分析する。

- ユーザが申告した故障内容
- 申告のうち、修理者が確認できたもの
- 修理者が確認した故障内容
- メーカー責任修理を含むか(YES/NO)
- 代表故障(修理者確認後の、メーカー責任の故障のうち最初に再現したもの)

### 1.2 経緯
- 旧方式(旧リポジトリ `IR_rep_categorize2`)は、①②③の丸数字を Python で機械的に分割していたが、「①②同じ部品で発生」「②原因は①要因」のような書き方で分割に失敗することが多かった。
- 2026-10-30〜11-02 に仕様を見直し、**LLM が番号ごとの対応づけを行う v2** を新しいリポジトリ `IR_rep_categorize_v2` として作り直した。旧リポジトリは記録として残している(変更しない)。

### 1.3 2台の PC での分担(重要)
| | Mac(個人、実データなし) | Windows(会社 PC、実データあり) |
|---|---|---|
| 担当 | Claude(このチャット)が仕様・テスト・実装・文書 | 担当者が環境構築・Dify・実データ実行・評価・調整。GPT(GPT 6.1 sol)はチャットだけで使う相談相手 |
| Python | 3.13 で開発 | 3.15、uv は使わない(pip + venv) |
| その他 | ー | Dify にアクセス可能 |

- **会社PCの GPT はチャットだけで使う**(2026-11-06 確認)。GPT はローカルのファイルを読み書きできず、コマンドも実行できない。コマンドの実行とファイルの変更は担当者が行い、GPT にはファイルをアップロードして渡す。GPT の変更案は「変更の指示」(文の形)で受け取り、担当者が Excel(YAML は codes-export / codes-import 経由)とテキストエディタ(プロンプト)で当てる。Windows 向けの資料・依頼文は、この前提で書く。
- **情報は Mac → Windows の一方向**(R-03)。会社 PC の情報は Mac に戻せない。人が手でメモできる短い情報だけを、ユーザがこのチャットに書き込む。
- **コードの受け渡しは GitHub**。Mac でユーザがコミットして push し、Windows 側は GitHub からリポジトリ全体を ZIP でダウンロードして、コードのフォルダを丸ごと置き換える。
- Windows 側で変更するファイル(YAML・プロンプト・`.env`・データ・結果)は、コードとは別の**ローカル作業フォルダ**(例: `C:\work\repclass_local`)に置く(R-05a)。そのため、**Mac 側で YAML やプロンプトを直しても、Windows のローカル作業フォルダには自動で反映されない**。担当者が手で追記するか、ファイルを置き換える。

## 3. 確定している仕様(要点。詳細は要件定義書)

### 3.1 行の単位と故障数
- 1行 = ユーザコメントの丸数字1つ。**故障数 = 丸数字(①〜⑳)の最大値**、無ければ 1(引用された番号があっても最大値で決まる)。
- 番号飛び(①③)の②は「申告なし(NO_CLAIM)」の空の行として残す。
- 記載のあるものはすべて故障数に数える(メンテナンス・ファームアップのみも含む)。

### 3.2 LLM の出力(1修理あたり)
- `claims`(番号ごと): user_code(ユーザ視点コード)、reproduction(ユーザ申告再現)、basis(direct / same_cause / none)、ref_sub_id、repair_code(修理者視点コード)、抜き出し
- `environment`: factor、source(user / repair / both)、abnormal_use、抜き出し
- `extra_findings`: 修理者側だけの発見
- 確信度(confidence)は出さない。内部コメントは当面 LLM に渡さない(`--include-internal` で切り替え可)。

### 3.3 ユーザ申告再現(6値)と判定ルール
| 値 | 「確認できた」に含む |
|---|---|
| reproduced(再現)/ partial(一部再現) | はい |
| not_reproduced(再現せず)/ not_mentioned(記載なし)/ out_of_scope(対象外)/ request_only(依頼のみ) | いいえ |

判定ルール(プロンプト R-31 に記載済み):
- キーワードではなく意味で判定。原因・所見・処置の記載があれば再現。
- **「現象を確認できなかった」が最優先**。エラー履歴や推定での部品交換は再現の根拠にしない。**例外**: ユーザ提出の画像・動画等の証左で確認できれば再現(現品で再現しなくても)。
- 「関連箇所を点検いたしましたが、異常はございませんでした」は再現せず。予防交換は再現せず。
- **設定・操作が原因**(設定解除後に異常なし)の場合は「再現」+ 設定・操作起因のコード。
- ユーザコメント側の「ご指摘外の現象」【ご指摘外の現象】は再現。
- 付随作業(※設定初期化、※最新ファームに更新)は処置とみなさない。ファーム更新そのもので改善した場合だけファームアップのコード。
- 前置き(「ショック品」= 衝撃、「メンテナンスで入庫しましたが修理に移行」= 通常の申告)も読む。事務的な【】(修理上限金額)は無視。

### 3.4 修理者視点コード
- 確認できた行: 実際の不具合のコード。再現せず・記載なし: 空。依頼のみ: 作業のサービスコード。対象外: 接続機器要因。
- **同原因(「②は①と同原因」)**: 再現は参照先から引き継ぎ(連鎖もたどる)、repair_code は**その行自身のユーザ視点コード**。まとめ書き(「①②同じ部品」)も同じ扱い。

### 3.5 メーカー責任修理を含むか(YES/NO)と代表故障
1. ユーザ起因の環境要因が1つでもあれば **NO**(修理全体)。落下・衝撃(ショック品含む)と水濡れ(雨含む)は常にユーザ起因。高温・低温・湿気・砂ほこりは「通常では考えづらい使用か」で判定。
2. そうでなく、確認できた行の repair_code + 追加の発見のうち、メーカー責任のコードが1つでもあれば **YES**。
3. 代表故障 = 確認できた行のうち、メーカー責任の repair_code で sub_id 最小のもの。無ければ追加の発見の最初。NO なら空。
- 責任区分はコードの `responsibility` で決まる。ファームアップで直る故障はユーザ責任(サービスコード)。

### 3.6 コード体系(YAML)
- 製品: ML(接頭文字 M)、LENS(L)、DC(コンパクトカメラ、D)。製品は YAML にセクションを足すだけで追加できる(Dify は共通プロンプト + コード一覧を変数で渡す)。
- 各製品に必須: 役割 connected_device(接続機器要因)/ other(その他)/ unknown(判定不能)を1つずつ、サービスコード1つ以上。自動チェック(`check`)で検証。
- その他(M046 / L036 / D048)は**メーカー責任**(ユーザ決定)。合うコードが無い修理は YES 側に倒れる点に注意。
- 主な追加・変更(2026-11-01〜03): 全コードの responsibility 設定(ユーザ決定: `docs/20261101_responsibility-set.csv`)、接続機器要因 M047 / L037、設定・操作起因 M048 / L038 / D047、レンズ表面 L039(L028 レンズ内との判定ルール、迷ったら表面)、DC 追加、DC はセンサー内ゴミを削除しセンサーゴミ D018 をメーカー責任に。

### 3.7 エラー時の動作
- エラーの修理は1件ずつ1回だけ自動で再試行。それでもエラーなら `status=error` として final.csv にも1行出し、判断の列は空欄(NO と区別)。`--resume <timestamp>` でエラー分だけ再実行し、全件そろった出力を作る。

### 3.8 評価
- 簡易版: 過去の分類結果(repair_id, representative_name)で YES/NO 一致率と代表故障の一致率。名称は NFKC 正規化 + 対応表(`eval_name_map.csv`)でコードに変換。
- 詳細版: 申告単位の正解(架空データの `expected_claims.csv` と同じ形式)。

## 5. これまでに発生した問題と解決方法

| 時期 | 問題 | 解決 |
|---|---|---|
| 〜10/30 | 丸数字の機械分割で、まとめ書き・番号の引用に対応できない | LLM に番号ごとの対応づけを任せ、故障数だけ Python で決める方式に変更 |
