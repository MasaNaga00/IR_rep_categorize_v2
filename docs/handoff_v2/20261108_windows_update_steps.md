## 1. 何が変わったか

実データの5つの例で、メーカー責任の判定が誤っていた。次のように直した。

| 例 | 直したこと | 直した場所 |
|---|---|---|
| 「雨に当たらないよう丁寧に扱っており」で水濡れ(ユーザ起因)になる | 否定・気をつけていたという文は環境要因にしない。修理者が水濡れ痕などを確認していれば、ユーザが否定していても環境要因にする | プロンプト |
| 「製品実力の範囲内ではございますが…調整」がメーカー責任になる | 新コード「製品実力範囲内」(ユーザ責任)。「規格内」「仕様の範囲内」なども対象 | YAML・プロンプト |
| 「◾️…⭐️バッテリーが劣化」で電源不良が追加される | 修理者コメントの注記(マークの後の文)を、Dify に渡す前に取り除く | プログラム・新しい設定ファイル |
| 「◾️レンズの防滴マウントゴムが破れて」でその他(メーカー責任)が追加される | 追加の発見(extra_findings)は参考の列に残すだけで、YES/NO・代表故障には使わない | プログラム |
| ディスプレイオフセンサーの汚れが LCD 表示不具合(メーカー責任)になる | 新コード「外部の汚れ(清掃で解消)」(ユーザ責任)。容易に拭き取れる接点の汚れも対象 | YAML・プロンプト |

**出力の変化**
- `final.csv`: `repair_confirmed_codes` に追加の発見のコードが入らなくなった。末尾に参考の列 `extra_finding_codes`、`extra_finding_names` を追加した。
- `repairs.csv`: 末尾に `user_comment_notes`、`repair_comment_notes`(取り除いた注記)を追加した。`repair_comment` は入力どおりの全文。
- 新しいファイル `removed_notes.csv`(取り除いた文と、Dify に渡した文の一覧。dry-run でも出る)。
- Tableau で `final.csv` を読み込んでいる場合は、列が2つ増える(既存の列の順番は変わらない)。

## 2. 手順

### 2-1. コードを新しい版に置き換え、テストを流す

```
python -m pytest tests/v2 -q
```

### 2-2. ローカル作業フォルダに新しい設定ファイルをコピーする
```
python repclass_cli.py init --local-dir C:\work\repclass_local
```
> 確認: `+ C:\work\repclass_local\comment_preprocess.yaml` が表示されること(ほかの既存のファイルは上書きされない)。

### 2-3. YAML に新しいコードを6つ足す
**ローカルの YAML に手を加えていない場合**: リポジトリの `config\classification_codes.yaml` で、ローカルの `classification_codes.yaml` を置き換える。

**手を加えている場合**: 次の6コードを足す(Excel で足すなら `codes-export` → 各製品のシートに行を追加 → `codes-import`)。説明文は、リポジトリの `config\classification_codes.yaml` から同じコードの `description` をコピーする。

| 製品のシート | コード | 名称 | 記録区分 | 責任区分 | 役割 |
|---|---|---|---|---|---|
| ML | M049 | 製品実力範囲内 | failure | user_or_unknown | (空) |
| ML | M050 | 外部の汚れ(清掃で解消) | failure | user_or_unknown | (空) |
| LENS | L040 | 製品実力範囲内 | failure | user_or_unknown | (空) |
| LENS | L041 | 外部の汚れ(清掃で解消) | failure | user_or_unknown | (空) |
| DC | D049 | 製品実力範囲内 | failure | user_or_unknown | (空) |
| DC | D050 | 外部の汚れ(清掃で解消) | failure | user_or_unknown | (空) |

```
python repclass_cli.py check --local-dir C:\work\repclass_local
```
> 確認: 置き換えた場合は `version=0.5.0 製品=ML(51), LENS(42), DC(50)`。足した場合は、各製品のコード数が2つずつ増えていること。

### 2-4. プロンプトを更新し、Dify に貼り直す
**ローカルのプロンプトに手を加えていない場合**: リポジトリの `config\prompts\v2\system_prompt.md` で、ローカルの `prompts\system_prompt.md` を置き換える。

**手を加えている場合**: リポジトリの `config\prompts\v2\system_prompt.md` から、次の6か所をコピーして、ローカルのプロンプトの同じ場所に足す(どれも「2026-11-08」の変更)。
1. 「# 入力」の `repair_comment` の行(「後ろに付く注記は、プログラムで取り除いてある」)
2. 「## 3. reproduction」の、「「製品実力の範囲内」「規格内」「仕様の範囲内」と書かれている場合も "reproduced"」の行
3. 「## 5. repair_code」の「**製品実力の範囲内の場合**」の段落と例2つ
4. 「## 5. repair_code」の「**外から触れる部分の汚れ**」の段落と例2つ
5. 「## 6. environment」の「**その環境に実際にさらされた…**」の段落と例3つ
6. 「## 7. extra_findings」の「修理と関係のない注記は出力しない」の行

最後に、`---` より下を Dify の LLM ノードの SYSTEM に貼り直し、公開する(手順書 手順5 の 4)。

### 2-5. 注記のマークを実データの文字に合わせる
手順書の **7-2a** の手順で行う。要点:
- Excel の `=DEC2HEX(UNICODE(MID(A2,15,1)))` でマークの文字コードを調べ、`comment_preprocess.yaml` の `note_markers` に `- "\u25A0"` の形で書く。
- dry-run で `注記を取り除いた修理: N 件` が 0 件でないこと、`removed_notes.csv` で取り除いた文が注記だけであることを確かめる。

### 2-6. 架空データで通しの確認をする
手順書の手順6と同じ。
> 確認: `dry-run: 入力 53 / 除外 2 / 送信予定 51 / バッチ 6`。本実行で `error 0`。
- 新しいシナリオは T046〜T053(`tests\fixtures\synthetic\README.md`)。評価(6-4)で T046〜T053 が外れていないかを見る。

### 2-7. 実データで、5つの例の型が直ったか確かめる
少量(50〜100件)で実行し、次を確かめる。
- 「雨に気をつけていた」のような否定の文の修理で、`environments.csv` に water が出ていないこと
- 「製品実力の範囲内」「規格内」の修理が、製品実力範囲内のコードで NO になっていること
- 注記(◾️⭐️※ など)のある修理で、`repair_confirmed_codes` に注記由来のコードが入っていないこと
- ディスプレイオフセンサー・接点の汚れの修理が、外部の汚れのコードで NO になっていること
