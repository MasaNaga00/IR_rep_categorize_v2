# 分類の定義を AI で直すときのプロンプト集(Windows 側・GPT 向け)

- 作成日: 2026-11-03
- 改訂: 2026-11-06 会社PCの GPT は**チャットだけ**で使い、ローカルのファイルを読み書きできず、コマンドも実行できない前提に書き直した。GPT にはファイルをアップロードして渡す。
- 目的: Mac 側で Claude と行った「分類の定義の修正」と同じことを、会社の PC の AI(GPT)で行うための依頼文のひな形。
- 使い方: 「3. 共通の前置き」を最初に貼り、続けて目的に合うひな形(A〜F)の `< >` の部分を埋めて貼る。ファイルは第2節のとおりに用意してアップロードする。

---

## 1. 役割分担と、1回の修正の流れ

| 担当 | 行うこと |
|---|---|
| 担当者 | コマンドの実行、ファイルの書き換え(Excel・テキストエディタ)、GPT へのアップロード、Dify への貼り直し、変更の承認 |
| GPT | アップロードされたファイルを読む。原因の切り分けと変更案を出す。承認された変更を、担当者がそのまま当てられる形(第4節)で出す。当てた後の照合 |

```
① 担当者: ファイルを用意してアップロード + 依頼文を貼る(第2節、第3節、A〜D)
② GPT   : 原因と変更案を表で出す
③ 担当者: 承認する(直してほしい点があれば伝える)
④ GPT   : 承認された変更を「変更の指示」の形で出す(第4節)
⑤ 担当者: YAML は Excel 経由、プロンプトはテキストエディタで当てる(第5節)
⑥ 担当者: check → Dify に貼り直す → 照合用のファイルをアップロード(E)
⑦ GPT   : 承認した変更だけが入っているかを照合する(E)
⑧ 担当者: 同じサンプルで再実行し、前後の結果をアップロード(F)
⑨ GPT   : 結果が変わった修理を一覧にする(F)
```

- GPT がファイルを作って出力できる場合(未確認)でも、変更は「変更の指示」(第4節)の形で受け取る。ファイルを丸ごと作り直させると、意図しない変更が混ざっても気づきにくいため。
- GPT のチャットは、新しく始めると前のファイルを覚えていない。**新しいチャットでは、そのときのローカル作業フォルダのファイルを毎回アップロードし直す**(正本はローカル作業フォルダ。R-04)。

## 2. アップロードするファイルの用意

### 2.1 ファイルの一覧

| ファイル | 場所 | 使う場面 |
|---|---|---|
| `classification_codes.yaml` | `C:\work\repclass_local\` | 毎回(今のコード体系) |
| `system_prompt.md` | `C:\work\repclass_local\prompts\` | 毎回(今のプロンプト) |
| `final.csv`、`claims.csv`、`environments.csv`、`extra_findings.csv` | `C:\work\repclass_local\outputs\<timestamp>\` | A(誤分類の原因を調べる)、F(前後の比較) |
| `mismatches.csv` | `<実行フォルダ>\evaluation\` | A(評価で見つかった不一致から直すとき) |
| `classification_codes.xlsx` | `codes-export` で書き出したもの | D(説明文の見直し) |
| 分類の一覧の CSV | 担当者が作る | B(新しい製品の追加) |
| `20261101_requirements.md`(要件定義書) | コードのフォルダの `docs\` | 任意。判断ルールの背景(R-31)を GPT に確かめさせたいとき |

### 2.2 注意
- **アップロードできない拡張子のとき**(例: `.yaml`、`.md` が受け付けられない): ファイルをコピーして拡張子を `.txt` に変えたものをアップロードする(例: `classification_codes.yaml.txt`)。中身は同じ。元のファイルの名前は変えない。
- **ファイルが大きすぎるとき**: 実行結果は、50〜100件程度の少量の実行のものを使う。全件の実行結果から必要な修理だけを取り出す場合は、Excel で行を絞って「CSV UTF-8(コンマ区切り)」で別の名前で保存する。
- 実行結果の CSV にはコメント本文が含まれる。会社の GPT にアップロードしてよいことは確認済み(2026-11-06)。**Mac 側への報告には、実データの内容を書かない**(第8節)。

## 3. 共通の前置き(毎回、最初に貼る)

```
あなたは修理データ分類パイプライン v2 の、分類コード体系(YAML)とプロンプトの調整を手伝う担当です。
あなたはファイルを直接変更できず、コマンドも実行できません。ファイルの変更とコマンドの実行は私(担当者)が行います。
あなたの役割は、アップロードされたファイルを読んで原因と変更案を出すこと、承認された変更を「変更の指示」の形で出すこと、私が当てた結果を照合することです。

【アップロードしたファイル】
- classification_codes.yaml(今の分類コード体系。正本)
- system_prompt.md(今の Dify のプロンプト。「---」の行より下を Dify に貼っている)
- <そのほかに添付したファイル>
(拡張子が .txt になっている場合は、中身は元のファイルと同じです)

【変えてよいもの】
- 分類コード体系の内容: コードの追加・削除、名称・説明文・判定ルール・記録区分・責任区分・役割・確認状態、環境要因。
  - YAML のキーの構造は変えない。私は YAML を直接ではなく、Excel(codes-export / codes-import)で直します。
  - コード番号は振り直さない。削除したコードは欠番にする。
- プロンプトの内容。ただし {{product_name}} と {{code_list}} の変数、JSON の出力形式(results / claims / environment / extra_findings の項目名と値の種類)は変えない。
- プログラム(src/、tests/)は変更しない。プログラムの不具合や仕様と違う点に気づいたら、変更案ではなく報告として書く。

【進め方】
1. いきなり変更の指示を出さず、まず「原因」と「変更案」を表で示し、私の承認を待つ。
2. 責任区分(responsibility)は業務上の判断なので、変える場合は案を出すだけにして、決めるのは私。
3. 分からない点・あいまいな点は、推測で進めずに質問する。ファイルに書かれていないことを、書かれているように言わない。
4. 承認されたら、変更の指示を次の形で出す。
   - YAML: Excel のセル単位の表(シート・コード・列・変更前・変更後)。列名は Excel の見出しと同じにする。
     製品シートの列: コード / 名称 / 説明文 / 記録区分 / 責任区分 / 役割 / 判定ルール / 確認状態
     環境要因シートの列: 要因 / 名称 / 説明文 / 常にユーザ起因 / キーワード(「、」区切り)
     変更後の値は、1セルずつコードブロックに入れる(そのままコピーして貼れるように)。
   - プロンプト: 変更ごとに「種類(追加/置き換え/削除)」「場所(見出しと、目印になる文)」「置き換え前の文(ファイルの文そのまま)」「新しい文」。
5. 変更の指示の最後に、私が行う作業の順番(Excel への入力 → codes-import → check、プロンプトの修正 → Dify への貼り直し)を短く書く。

【分類の考え方(決定済み)】
- 修理者視点コードの責任区分で「メーカー責任修理を含むか」を決める。判断(YES/NO・代表故障)はプログラムが行い、LLM は事実(コード・再現・環境要因・抜き出し)だけを出す。
- メーカー責任として数えるのは、修理者が現象を確認できた(再現・一部再現)申告だけ。
- 判断に迷う組(センサー内/表面、レンズ内/表面 など)は、決めた側に倒すルールを説明文と判定ルールに書く。
- AI が書いた説明文は確認状態を ai_inferred にし、私が確認したものを verified にする。
- プロンプトに足す例は、架空の短い例にする。実データの文をそのまま例にしない。
```

```
- 場所: 見出し「## 5. repair_code(修理者視点コード)」の中
- 置き換え前の文:
  <ファイルの文そのまま>

  <変更後の文>
```

## 5. 担当者が変更を当てる手順

### 5.1 YAML(Excel 経由)
1. Excel に書き出す(すでにあれば `--force` で書き出し直す。古い Excel を使うと、その後の YAML の変更が消えるため)。
   ```
   python repclass_cli.py codes-export --local-dir C:\work\repclass_local --force
   ```
2. `C:\work\repclass_local\classification_codes.xlsx` を開き、変更の指示の表のとおりに直して保存する。
   - 新しいコード: 製品シートに行を足す。記録区分・責任区分・役割・確認状態はドロップダウンで選ぶ。
   - 削除: その行を削除する(番号は振り直さない)。
   - 新しい製品: シート `製品設定` に行を足し、既存の製品シートをコピーして、製品IDと同じ名前に変えて中身を入れ替える。
3. YAML に取り込む。
   ```
   python repclass_cli.py codes-import --local-dir C:\work\repclass_local --xlsx C:\work\repclass_local\classification_codes.xlsx
   ```
   - 問題があれば YAML は書き換えられず、問題の一覧が出る。一覧を GPT に貼って直し方を聞いてよい。
   - 成功すると、製品ごとに「追加・変更・削除」されたコードの一覧が出る。この表示を控える(E で使う)。元の YAML は `classification_codes_日時.bak.yaml` として残る。
4. チェックする。
   ```
   python repclass_cli.py check --local-dir C:\work\repclass_local
   ```

### 5.2 プロンプト
1. `C:\work\repclass_local\prompts\system_prompt.md` をコピーして、変更前の版として残す(例: `system_prompt_20261106_before.md`)。
2. テキストエディタ(メモ帳、VS Code など)で `system_prompt.md` を開き、変更の指示のとおりに直す。保存するときの文字コードは UTF-8。
3. Dify に反映する(どちらか)。
   - Dify の LLM ノードの SYSTEM の中で、同じ箇所を同じように直す(変更が少ないとき)。
   - または、`---` の行より下をすべて貼り直し、`{{product_name}}` と `{{code_list}}` を Dify の変数挿入で入れ直す(`docs\dify\v2_workflow_setup.md` の 2.3)。
4. Dify で「公開」を押す。

## A. 誤分類を直す(一番よく使う)

誤った修理を数件まとめて渡すと、原因の切り分けから対策案まで出してもらえる。

**アップロードするもの**: `classification_codes.yaml`、`system_prompt.md`、その実行の `final.csv`・`claims.csv`・`environments.csv`・`extra_findings.csv`(評価で見つけた場合は `mismatches.csv` も)

```
次の修理が誤って分類されています。原因を切り分けて、直し方を提案してください。

【誤った修理】(数件まとめて書く。コメント本文は、添付の final.csv にはありません。原文が必要なので下に書きます)
1. 修理ID: <ID>
   - ユーザコメント: <…>
   - 修理者コメント: <…>
   - 今の結果: <例: 修理者視点コード=動作不良、メーカー責任修理=YES>
   - 正しい結果: <例: メーカー責任ではない(NO)>
2. …

【正しい判断の理由(業務ルール)】
<例: カメラの設定が原因で、部品の不具合が無い場合はメーカー責任ではない>

【やってほしいこと】
1. 添付の claims.csv・environments.csv・extra_findings.csv で各修理の行を確認し、原因が次のどれかを判断する。
   ① repair_code の選び間違い(合うコードが無い場合を含む)
   ② reproduction(再現の判定)の誤り
   ③ 環境要因の誤り
   ④ コードの責任区分が実態と合っていない
   ⑤ プロンプトのルール同士が競合している
2. 原因ごとに、次のどれで直すかを提案する(表で)。
   - 既存コードの説明文・判定ルールを具体的にする
   - 新しいコードを追加する(名称・説明文・記録区分・責任区分の案)
   - プロンプトの該当する規則に、指示と「架空の短い例」を1つ追加する
   - ルールが競合する場合は、どちらを優先するかを明記する
3. 直したときに、ほかの修理の結果が悪くなるおそれがあれば書く。
4. 私の承認後に、変更の指示(第4節の形)を出す。
```

- コメント本文は `repairs.csv` にも入っている。件数が少なければ `repairs.csv` を添付し、依頼文には修理IDだけを書いてもよい。
- 変更を当てた後は、E(照合)と F(前後の比較)に進む。

**これまでの修正から分かったコツ**
| よくある原因 | 直し方の例(2026-11-03 の実例) |
|---|---|
| 合うコードが無く、近いコード(動作不良・その他)に逃げている | 新しいコードを追加する(例: 設定・操作起因 M048) |
| 指示同士が競合している(「処置の記載→再現」と「確認できず→再現せず」) | 優先順位を明記する(例: 「確認できなかった」が最優先。エラー履歴・推定交換は根拠にしない) |
| 内側と外側の区別が無い | 組のコードを作り、迷ったらどちらに倒すかを書く(例: レンズ内 L028 / レンズ表面 L039) |
| 例外がある | 例外の条件と例を書く(例: ユーザ提出の画像で確認できた場合は再現) |

## B. 新しい製品を追加する

**アップロードするもの**: `classification_codes.yaml`、`system_prompt.md`、分類の一覧の CSV(列: 分類, responsibility, record_type)

```
新しい製品を分類コード体系に追加してください。

【製品】
- 製品ID: <例: DC>(入力 CSV の製品種別の列の値と同じにする)
- 表示名: <例: コンパクトカメラ>
- 接頭文字: <例: D>

【分類の一覧】添付の CSV(列: 分類, responsibility, record_type)

【やってほしいこと】
1. 一覧の順にコード番号を振る(<接頭文字>001 から。判定不能は <接頭文字>_UNK)。
2. 次の役割を付ける: 接続機器要因 = connected_device、その他 = other、判定不能 = unknown。
   各製品に connected_device・other・unknown が1つずつと、記録区分 service のコードが1つ以上必要です。足りなければ質問してください。
3. 説明文は、既存の製品(ML・LENS)の同じ名前の分類にそろえ、似た分類どうしの境目
   (例: 電源不良とフリーズ、ズーム動作不良と鏡筒の異音)を書き込む。確認状態は ai_inferred。
4. 内側/表面のような組があれば、迷ったときにどちらに倒すかの判定ルールを付ける。
5. 一覧の誤字や、責任区分・記録区分で疑問がある分類は、変更せずに質問として列挙する。
6. 私の承認後に、変更の指示を出す。
   - シート「製品設定」に足す1行(製品ID / 表示名 / 接頭文字)
   - 新しい製品シートの全行。この場合はセル単位ではなく、1行=1コードの表で出す(列: コード / 名称 / 説明文 / 記録区分 / 責任区分 / 役割 / 判定ルール / 確認状態)。説明文・判定ルールに改行は入れない。
   - プロンプトに製品ごとの指示が必要なら、その変更の指示
7. 私が codes-import の結果を貼ったら、CSV と照合して、分類名・責任区分・記録区分が一致しているかを報告する。
```

- 新しい製品のシートは行数が多いので、表を Excel にまとめて貼ってよい(改行が無い表に限る)。貼った後、列がずれていないかを確かめる。

**アップロードするもの**: 変更後の `classification_codes.yaml`、変更後の `system_prompt.md`(同じチャットでない場合は、変更前の YAML(`.bak.yaml`)と変更前のプロンプトも)

```
<check の表示をそのまま貼る>
```

## F. 変更前と変更後の結果を比べる

**担当者が先に行うこと**: 変更前と同じ入力 CSV で実行する(正解ファイルがあれば `evaluate` も)。
```
python repclass_cli.py run --input <変更前と同じCSV> --local-dir C:\work\repclass_local
python repclass_cli.py evaluate --gold <正解CSV> --run C:\work\repclass_local\outputs\<timestamp> --local-dir C:\work\repclass_local
```

## 6. 依頼文を書くときのコツ

- **正しい答えだけでなく、理由(業務ルール)を書く**。理由があると、AI は同じ型の別のケースにも効く直し方を出せる。
- **誤った例は数件まとめて渡す**。1件だけだと、その1件にしか効かない直し方になりやすい。
- **「まず提案、承認後に変更の指示」を毎回指示する**。分類の定義は集計結果に直結するため。
- **プロンプトに足す例は架空の短い例にする**。実データの文をそのまま貼らない。
- **直したら同じサンプルで前後を比べる**(F)。良くなったケースと悪くなったケースの両方を見る。
- **変更を当てたら照合する**(E)。手で当てるので、入れ忘れ・入れ間違いが起こりうる。

## 7. ファイルの扱いのルール

- 変更するのは、ローカル作業フォルダ(`C:\work\repclass_local`)の中のファイルだけ。コードのフォルダ(`src\`、`tests\` ほか)は変更しない(R-01、R-02)。
- 変更前の版を残す: YAML は codes-import が自動で `.bak.yaml` を作る。プロンプトは 5.2 の1のとおり手でコピーする。
- どの実行でどの YAML・プロンプトを使ったかは、`run_meta.json` のハッシュ値(`codebook_sha256`、`prompt_sha256`)で区別できる。
