# 分類の定義を AI で直すときのプロンプト集(Windows 側・GPT 向け)

- 作成日: 2026-11-03
- 目的: Mac 側で Claude と行った「分類の定義の修正」と同じことを、会社の PC の AI(GPT)で行うための依頼文のひな形。
- 使い方: 「0. 共通の前置き」を最初に貼り、続けて目的に合うひな形(A〜D)の `< >` の部分を埋めて貼る。

---

## 0. 共通の前置き(毎回、最初に貼る)

```
あなたは修理データ分類パイプライン v2 の、分類コード体系とプロンプトの調整を手伝う担当です。
次のルールを守ってください。

【読む文書】
- docs/handoff_v2/20261102_windows_handoff.md(作業ルール)
- docs/20261101_requirements.md の R-31(判断の指示)と第12節(Excel 入出力)

【変更してよいもの】
- ローカル作業フォルダ C:\work\repclass_local の中だけ。
  - classification_codes.yaml(分類コード体系)
  - prompts\system_prompt.md(Dify に貼るプロンプト)
- src\ と tests\ は変更しない。YAML のキーの構造も変えない。

【進め方】
1. いきなり変更せず、まず「原因」と「変更案」を表で示し、私の承認を待つ。
2. 責任区分(responsibility)は業務上の判断なので、変える場合は案を出すだけにして、決めるのは私。
3. 分からない点・あいまいな点は、推測で進めずに質問する。
4. 承認後に変更したら、次を必ず行う。
   - python repclass_cli.py check --local-dir C:\work\repclass_local(OK になること)
   - プロンプトを変えた場合は、Dify に貼り直す手順を私に示す
   - 変更した箇所の一覧(ファイル・コード・変更前 → 変更後)を報告する

【分類の考え方(決定済み)】
- 修理者視点コードの責任区分で「メーカー責任修理を含むか」を決める。
- メーカー責任として数えるのは、修理者が現象を確認できた(再現・一部再現)申告だけ。
- 判断に迷う組(センサー内/表面、レンズ内/表面 など)は、決めた側に倒すルールを説明文と判定ルールに書く。
- AI が書いた説明文は description_status を ai_inferred にし、私が確認したものを verified にする。
```

## A. 誤分類を直す(一番よく使う)

誤った修理を数件まとめて渡すと、原因の切り分けから対策案まで出してもらえる。

```
次の修理が誤って分類されています。原因を切り分けて、直し方を提案してください。

【誤った修理】(数件まとめて書く)
1. 修理ID: <ID>(実行フォルダ: <C:\work\repclass_local\outputs\timestamp>)
   - ユーザコメント: <…>
   - 修理者コメント: <…>
   - 今の結果: <例: 修理者視点コード=動作不良、メーカー責任修理=YES>
   - 正しい結果: <例: メーカー責任ではない(NO)>
2. …

【正しい判断の理由(業務ルール)】
<例: カメラの設定が原因で、部品の不具合が無い場合はメーカー責任ではない>

【やってほしいこと】
1. 実行フォルダの claims.csv と environments.csv で各修理の行を確認し、原因が次のどれかを判断する。
   ① repair_code の選び間違い(合うコードが無い場合を含む)
   ② reproduction(再現の判定)の誤り
   ③ 環境要因の誤り
   ④ コードの責任区分が実態と合っていない
   ⑤ プロンプトのルール同士が競合している
2. 原因ごとに、次のどれで直すかを提案する(表で)。
   - 既存コードの説明文・判定ルールを具体的にする
   - 新しいコードを追加する(名称・説明文・記録区分・責任区分の案)
   - プロンプトの該当する規則に、指示と「架空の短い例」を1つ追加する
   - ルールが競合する場合は、どちらを優先するかを明記する
3. 承認後に変更し、同じサンプルと架空データ(tests\fixtures\synthetic\repairs.csv)で再実行・評価して、
   修正前と比べて結果が変わった修理を一覧で報告する。
```

**これまでの修正から分かったコツ**
| よくある原因 | 直し方の例(2026-11-03 の実例) |
|---|---|
| 合うコードが無く、近いコード(動作不良・その他)に逃げている | 新しいコードを追加する(例: 設定・操作起因 M048) |
| 指示同士が競合している(「処置の記載→再現」と「確認できず→再現せず」) | 優先順位を明記する(例: 「確認できなかった」が最優先。エラー履歴・推定交換は根拠にしない) |
| 内側と外側の区別が無い | 組のコードを作り、迷ったらどちらに倒すかを書く(例: レンズ内 L028 / レンズ表面 L039) |
| 例外がある | 例外の条件と例を書く(例: ユーザ提出の画像で確認できた場合は再現) |

## B. 新しい製品を追加する

```
新しい製品を分類コード体系に追加してください。

【製品】
- 製品ID: <例: DC>(入力 CSV の製品種別の列の値と同じにする)
- 表示名: <例: コンパクトカメラ>
- 接頭文字: <例: D>

【分類の一覧】(添付の CSV。列: 分類, responsibility, record_type)
<CSV を貼る、または添付>

【やってほしいこと】
1. 一覧の順にコード番号を振る(<接頭文字>001 から。判定不能は <接頭文字>_UNK)。
2. 次の役割を付ける: 接続機器要因 = connected_device、その他 = other、判定不能 = unknown。
3. 説明文は、既存の製品(ML・LENS)の同じ名前の分類にそろえ、似た分類どうしの境目
   (例: 電源不良とフリーズ、ズーム動作不良と鏡筒の異音)を書き込む。description_status は ai_inferred。
4. 内側/表面のような組があれば、迷ったときにどちらに倒すかの判定ルールを付ける。
5. 一覧の誤字や、責任区分・記録区分で疑問がある分類は、変更せずに質問として列挙する。
6. 追加後に check を実行し、CSV と YAML を1行ずつ照合した結果(分類名・責任区分・記録区分の一致)を報告する。
```

## C. 責任区分の変更・コードの削除

```
分類コード体系を次のとおり変更してください。

【変更内容】
- <例: DC の「センサー内ゴミ」を削除し、「センサーゴミ」をメーカー責任に変更>
【理由】
- <例: コンパクトカメラはユーザがセンサーに触れられないため>

【やってほしいこと】
1. 削除するコードの番号は振り直さず、欠番にする。
2. ほかのコードの説明文・判定ルールで、削除・変更したコードに触れている箇所も直す。
3. 判断の根拠が私の決定なので、変更したコードの description_status は verified にする。
4. check を実行し、変更した箇所の一覧を報告する。
```

## D. 説明文をまとめて見直す

```
分類コード体系の説明文を見直したいです。
1. python repclass_cli.py codes-export --local-dir C:\work\repclass_local で Excel に書き出してください。
2. シート <例: DC> の説明文を読み、次の観点で問題がある分類を表にしてください(変更はまだしない)。
   - 似た分類どうしの境目が書かれていない
   - 説明文と名称が合っていない
   - 責任区分が説明文の内容と矛盾しているように見える(提案だけ)
3. 私が承認した分だけ Excel を直し、codes-import で YAML に戻し、check の結果と変更の一覧を報告してください。
```

## 依頼文を書くときのコツ

- **正しい答えだけでなく、理由(業務ルール)を書く**。理由があると、AI は同じ型の別のケースにも効く直し方を出せる。
- **誤った例は数件まとめて渡す**。1件だけだと、その1件にしか効かない直し方になりやすい。
- **「まず提案、承認後に変更」を毎回指示する**。分類の定義は集計結果に直結するため。
- **プロンプトに足す例は架空の短い例にする**。実データの文をそのまま貼らない。
- **直したら同じサンプルで前後を比べる**。良くなったケースと悪くなったケースの両方を見る。

## Mac 側(リポジトリの初期値)にも反映したいとき

Windows 側の変更は Mac に戻らない(R-03)。リポジトリの初期値・架空データ・テストにも入れたい決定は、担当者が次の形で短くメモして Mac 側のチャットに伝える。

```
[分類] <製品>: <決定内容を1〜2行>。例: <架空の短い例>
例) [分類] DC: センサー内ゴミを削除、センサーゴミをメーカー責任に。ユーザが触れられないため。
```
