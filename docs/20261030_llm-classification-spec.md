## 1. 背景

これまで、ユーザコメントと修理者コメントを `split.py` で①②③ごとに機械的に分割していた。しかし、次のようなケースで正しく分割できないことが多かった。

- 修理者コメントで複数の番号をまとめて書いている
  - 例: 「①②同じ電気部品が問題で発生」
- 別の番号の説明の中で、番号が引用として出てくる
  - 例: 「②原因は①要因でした」

そこで、番号と内容の対応づけを LLM に任せる方式に見直す。

## 2. 基本方針

- 【確定】ユーザの申告を軸にする。ユーザコメントの番号ごとに、修理者コメントで確認できたかを判断させる。
- 【確定】故障数(=行の数)は機械的に決め、番号と内容の対応づけを LLM が担う。
- 【確定】LLM の呼び出しは**1回**にする(ユーザコメントの分解と修理者コメントとの照合を1回で行う)。
  - 故障数を Python で固定して渡すため、2段階に分ける必要性が下がった。
  - 検証(第12節)で、ユーザ側の分解での間違いが多ければ、2段階(LLM ノードを2つ直列)に分けることを検討する。

## 3. 行の単位と故障数

- 【確定】1行 = ユーザコメントの丸数字1つ。主キーは `(repair_id, sub_id)`。
- 【確定】故障数 = ユーザコメント中の**丸数字の最大値**。
  - ユーザコメント内で別の番号を引用することがあるため、出現回数ではなく最大値を使う。
- 【確定】丸数字が無い場合、故障数は1。
- 【確定】内容が他の番号と重複していても、番号ごとに1行として扱う。
- 【確定】番号が飛んでいる場合(例: ①③のみ)も、②を**空の行として残す**。警告だけだと読み飛ばすため。
  - 【確定】空の行のユーザ視点コードには「申告なし」を表す専用の値を入れ、フィルターで見えるようにする。
- 【確定】故障数は Python で計算して LLM に渡す。LLM の出力件数と合わなければ検出する。
- 【確定】丸数字は⑳まで対応する。

## 4. 出力カラム(1行あたり)

| カラム | 内容 | 状態 |
|---|---|---|
| ユーザ視点コード | ユーザが訴えた現象の故障コード | 【確定】 |
| ユーザ申告再現 | ユーザの申告が修理者の手元で確認されたか(値は第5節) | 【確定】 |
| 修理者視点コード | 修理者が特定した実際の不具合の故障コード | 【確定】 |
| 再現の根拠の種類 | 直接確認 / 他の番号と同原因 など | 【確定】 |
| 参照先の番号 | 他の番号を経由して判断した場合の番号 | 【確定】 |
| 根拠の抜き出し | 判断に使った原文の抜き出し(原文に含まれるかを Python で検証) | 【確定】 |
| 環境要因 | 第7節 | 【確定】(別カラム) |
| 記録区分 | 故障 / サービスのみ(第8節) | 【確定】(別カラム) |

- 【確定】ユーザ視点コードとユーザ申告再現を分けて持つことで、ユーザの申告が再現した情報が記載されているかを確認できるようにする。
- 読み方の例: 「ユーザ視点コード ≠ 修理者視点コード」かつ「ユーザ申告再現 = 再現」なら、申告された現象は事実だったが、原因は別の部位にあったと読める。

## 5. 「ユーザ申告再現」の値【確定】

| 値 | 意味 |
|---|---|
| 再現 | 修理者が確認したと記載している(他の番号経由を含む) |
| 一部再現 | 条件付きで再現、または一部の症状だけ再現 |
| 再現せず | 確認したが再現しなかったと記載している |
| 記載なし | その番号について再現の有無が読み取れない |
| 対象外 | 「レンズ側で対応」など、この製品では扱っていない |
| 依頼のみ | 点検・清掃などの依頼で、不具合の訴えがない(2026-11-01 追加) |

「再現せず」と「記載なし」は必ず区別する。

- 【確定】不具合の訴えがない依頼(点検・清掃など)は「依頼のみ」とし、「記載なし」(修理者コメントの書き漏れの目印)と混ぜない。
- 【確定】訴えがある場合は、対処がサービス作業(例: ファームアップ)でも通常どおり判定する。
  - 例: 「AFが不安定」→ 修理者が再現を確認 → ファームアップで対応 → 「再現」
- 「確認できた」に含めるのは「再現」と「一部再現」(第14.5節)。

## 6. 他の番号を参照する修理者コメントの扱い【確定】

例: 「②は①と同じ原因で発生していたと考えます」

- ②のユーザ申告再現は、①の結果を**そのまま引き継ぐ**。
  - ①が「再現」なら②も「再現」、①が「再現せず」なら②も「再現せず」。
- ②の修理者視点コードは、**②自身のユーザ視点コード**とする(2026-11-02 変更。ユーザが申告した現象が実際に起きていた、とみなすため。旧: ①のコードを引き継ぐ案A)。
- ②のユーザ視点コードは、②の申告内容に沿って付ける(①とは異なってよい)。

例:

| 番号 | ユーザ視点コード | ユーザ申告再現 | 修理者視点コード | 根拠の種類 | 参照先 |
|---|---|---|---|---|---|
| ① | 電源系 | 再現 | 電源系(電源基板) | 直接確認 | - |
| ② | 液晶表示系 | 再現 | 液晶表示系(②自身のユーザ視点コード) | 他の番号と同原因 | ① |

### 6.1 「対象外」の行の修理者視点コード【確定】

- 「対象外」の行にも、修理者コメントの内容から修理者視点コードを付ける(空欄にしない)。
- 「レンズ側で対応、カメラには異常なし」のように**接続機器が原因**の場合は、YAML に追加する「接続機器要因」コードを付ける。このコードはメーカー責任ではない(第15節)。
- 注意: 修理者が確認していないのにメーカー責任コードが付くと、YES/NO が誤って YES になる。検証(第12節)で重点的に確認する。

## 7. 環境要因

- 【確定】環境要因(衝撃・落下・水没など)は別カラムに抽出する。
  - ユーザの取り扱いが修理の原因かどうかを判断するための重要な情報。
- 【確定】要因の種類に加えて、**誰の記述が根拠か**(user / repair / both)も残す。
  - ユーザ自身が「落とした」と書いているのか、修理者が「打痕あり」と見つけたのかで、証拠としての重みが違うため。
  - 既存スキーマの `environment_evidence_source` の考え方を流用する。

## 8. サービス記録(メンテナンス・ファームアップのみ)と集計方針

- 【確定】**記載のあるものは最初はすべて残し、すべて故障数として数える**。
  - メンテナンスのみ・ファームアップのみの修理も含む。
- 【確定】記録区分(故障 / サービス)の列は、除外のためではなく**フィルター用の情報**として持つ。
- 【確定・反映済み 2026-11-01】YAML のサービスコード(M042〜M045 / L032〜L035)の説明文から「故障ではなく」を削除し、`responsibility: user_or_unknown` を明記した。
- 【確定】ファームアップで直る場合は、ユーザ責任として判断する。
  - ファームは配布済みのため、メーカー側の問題ではないという考え方。
  - 修理者視点コードがファームアップ(M045 / L035)になることで、メーカー責任ではないと判定される。
    - 確認済み: YAML の M045 / L035 には responsibility が設定されていない(未定義)。`codes_loader.is_manufacturer_responsibility()` は未定義を False(メーカー責任ではない)として返す。
    - 【確定・反映済み 2026-11-01】意図を明確にするため、サービスコードにも `responsibility: user_or_unknown` を明記した。
  - ユーザ視点コードがメーカー責任のコードであれば、`is_misjudged`(ユーザ視点と修理者視点で責任が食い違う)にも表れる。
- 【確定】最終的な解析は、メーカー責任の故障に絞って行う(responsibility で絞り込む)。
- 【確定】記録区分は、修理者視点コードの `record_type` から Python で判定する(LLM に別途書かせない)。
  - ML: M042〜M045、LENS: L032〜L035
- 【確定】記録区分は、修理単位ではなく番号(行)単位で持つ。

## 9. 修理者側の追加の発見

- 【確定】ユーザが申告していない、修理者側だけの発見(例: 「別途○○の劣化あり」)は、**別の枠に記録する**。
- 【確定】記録の形は、第14.4節の「④ 追加の発見表」とする。

## 10. 内部コメント(Internal_1 / Internal_2)

- 【確定】最初は内部コメントを使わずに分類する。必要と分かったら追加する。
  - 理由: 「衝撃を受けたように見えるが初回なので請求しない」のような対応上の判断が含まれており、分類の判断を迷わせる可能性があるため。
  - ただし、分類に関わる内容が書かれている場合もある(具体例は未収集)。
- 【確定】検証サンプルを作るときに、「内部コメントを読まないと正しく分類できない例」に印を付けて具体例を集める。
- 【確定】集まった例を見てから、使い方を決める。
  - 分類の材料として入れる
  - 「対応上の扱い」を記録する別カラムにする
  - 両方
- 【確定】導入するかどうかは、同じサンプルを内部コメントあり・なしで処理し、結果の差を見て判断する。

## 14. データ構造

### 14.1 基本の考え方【確定】

- LLM には番号ごとの「事実」だけを出力させる。
  - 例: 故障コード、再現状況、環境要因、根拠の抜き出し
- 「判断」はすべて Python で中間データから計算する。
  - 例: メーカー責任修理の YES/NO、代表故障
- こうしておけば、判断ルールを変えても LLM を再実行せずに出し直せる。

### 14.2 入力【確定】

| 列 | 内容 |
|---|---|
| 修理ID | 主キー |
| 製品種別 | ML / LENS(コード体系の切り替えに使う) |
| ユーザコメント | |
| 修理者コメント | |
| 内部コメント1 | 当面は分類に使わない(第10節) |
| 内部コメント2 | 同上 |

### 14.3 データの3層

```
[入力]
  ↓ Python: 丸数字の最大値 → 故障数
  ↓ LLM(Dify)
[層1: 生出力] LLM の応答 JSON をそのまま保存(実行日時・プロンプトの版と一緒に)
  ↓ Python: 検証して表に展開
[層2: 中間データ] 4つの表
  ↓ Python: 判断ルールを適用(YAML を参照)
[層3: 最終出力] 修理ID単位の表(Tableau 用)
```

### 14.4 層2: 中間データ(4つの表)

コード名、responsibility、記録区分は中間データに持たせない。YAML から毎回引くことで、YAML の修正が自動で反映されるようにする。【確定】

- 【確定】その代わり過去の集計結果が後から変わり得るため、各実行で使った YAML の版(バージョンとファイルのハッシュ値)を実行メタ情報に記録する。

**① 修理表**(1行 = 1修理)

| 列 | 内容 |
|---|---|
| 修理ID | |
| 製品種別 | |
| 故障数 | ユーザコメントの丸数字の最大値(無ければ1) |
| 元のコメント一式 | 入力の5列 |
| 処理状態 | 成功 / 失敗(失敗は再実行の対象) |

**② 申告表**(1行 = ユーザの番号1つ)※中心となる表

| 列 | 内容 |
|---|---|
| 修理ID | |
| 番号 | sub_id(1始まり) |
| ユーザ申告の抜き出し | |
| ユーザ視点コード | 番号が飛んでいる場合は「申告なし」 |
| ユーザ申告再現 | 再現 / 一部再現 / 再現せず / 記載なし / 対象外 / 依頼のみ |
| 再現の根拠の種類 | 直接確認 / 他の番号と同原因 など |
| 参照先の番号 | |
| 修理者視点コード | 他の番号と同原因の場合は参照先のコードを引き継ぐ |
| 修理者コメントの抜き出し | |

- 【確定】ユーザコメントに「修理中に見つかった現象」として書かれているものも、ユーザ視点の故障現象として扱う。区別するための列は設けない。

**③ 環境要因表**(1行 = 要因1つ)

| 列 | 内容 |
|---|---|
| 修理ID | |
| 要因 | 落下・衝撃、水没、高温、低温、湿気、砂・ほこり など |
| 誰の記述か | user / repair / both |
| ユーザ起因か | はい / いいえ |
| 根拠の抜き出し | |
| 対象の番号 | 任意(記録用。判定には使わない) |

- 【確定】通常では考えづらい使用環境であれば、ユーザ起因とする。
- 【確定】「ユーザ起因か」の決め方は2通りに分ける。
  - 落下・衝撃、水没: 常に「はい」(Python で機械的に判定)
  - 高温、低温、湿気、砂・ほこり: LLM に「通常では考えづらい使用か」を判定させ、根拠も出させる

**④ 追加の発見表**(1行 = 修理者側だけの発見1つ)

| 列 | 内容 |
|---|---|
| 修理ID | |
| 内容 | |
| 修理者視点コード | |
| 根拠の抜き出し | |

- 通常、修理者の発見はユーザコメントに番号付きで書かれるため ② に入る。④ はその運用から漏れたものを拾う保険の位置づけ。

### 14.5 層3: 最終出力(1行 = 1修理)【確定】

| 列 | 計算の仕方 |
|---|---|
| ユーザ申告の故障内容 | ② のユーザ視点コードを番号順に並べる |
| 申告のうち修理者が確認できたもの | ② でユーザ申告再現が「再現」または「一部再現」のもの |
| 修理者が確認した故障内容 | ② のうち確認できた行(再現・一部再現)の修理者視点コード + ④ の修理者視点コード(2026-11-02 確定) |
| メーカー責任修理を含むか | 下記の判定ルール |
| 代表故障 | 下記の選び方 |

**メーカー責任修理を含むか(YES/NO)**

1. ③ にユーザ起因の環境要因が1つでもある → **NO**
   - 落下に限らず、水没や炎天下の車内なども含め、修理全体をユーザ責任とする。
2. そうでなく、「修理者が確認した故障内容」(確認できた行 + ④)のうち、メーカー責任のものが1つでもある → **YES**
3. それ以外 → **NO**

**代表故障**

1. ② のうち、ユーザ申告再現が「再現」または「一部再現」で、修理者視点コードがメーカー責任の行を集める。その中で**番号が最も小さい行**の修理者視点コードを代表故障とする。
   - 今の運用ルール「ユーザ申告のうち最初に再現した故障」をそのままコードにしたもの。
2. 1 に該当する行がなく、④ だけで YES になった場合は、**④ の最初の発見**の修理者視点コードを代表故障とする。
3. YES/NO が NO の修理は、代表故障なし(空欄)とする。【確定】

### 14.6 保存形式【確定】

- 層1: JSON(実行ごとに1ファイル)
- 層2・層3: CSV(UTF-8)。Parquet は出力しない(2026-11-02 変更)
  - CSV は Tableau で読み込むため。
- 実行ごとにタイムスタンプを付け、層1〜3を同じタイムスタンプで対応づける。

## 15. YAML(classification_codes.yaml)の変更

## 16. 製品種別の拡張(ML / LENS 以外への対応)

### 16.1 背景

- 将来、ML / LENS 以外の製品(ストロボ、プリンター、コンパクトカメラ等)も対象に加える予定。
- 確認済み(2026-11-01): 現状、ML / LENS は次の4か所に直接書き込まれている。
  - `src/codes_loader.py`: `ProductType` の Enum
  - `src/dify_client.py`: 製品種別のチェック(`("ML", "LENS")`)
  - `src/prompt_builder.py`: 製品の表示名、CLI の選択肢など
  - Dify ワークフロー: 製品ごとの if/else 分岐と、製品ごとのシステムプロンプト

### 16.2 方針【確定】

- **製品の追加 = YAML に製品セクションを足すだけ**で済む形にする。
- YAML: 製品ごとに、表示名・コードの接頭文字・故障コード一式を持たせる。
  - 故障コード一式には、responsibility、サービスコード、接続機器要因を含む。
- Python: 製品の一覧を YAML から読み込み、ML / LENS の直接の記述をなくす。
- Dify: 製品ごとの分岐をやめ、**共通のプロンプト1つ**にする。その製品のコード一覧は、呼び出しのたびに変数として渡す。
  - 旧方針「プロンプトは Dify に固定」を一部変更する。判断ルールは Dify に固定し、コード一覧だけを外から渡す。
  - 製品を追加しても、Dify 側は直さずに済む。
  - その代わり、コード一覧の分だけトークンが増える(50コード程度なら小さい)。
- 判断ロジック(故障数・YES/NO・代表故障、第14節)は製品に依存しないので、共通で使う。

### 16.3 設計上の決定【確定】

- コードの接頭文字は固定の割り当てを作らず、**製品セクションごとに YAML で決める**(例: S = ストロボ、P = プリンター、C = コンパクトカメラ)。
- 環境要因(第7節・第14.4節③)の一覧とユーザ起因の判定基準を、製品ごとに持てるようにする。
  - 例: プリンターでは「純正以外のインク」「異物の混入」など、ユーザ起因になる要因の種類が変わる可能性がある。
- コンパクトカメラは ML とコードの多くが共通になりそうだが、責任の判断が変わる可能性もある。そのため、共有せずに別セクションとしてコピーして持つ。

### 16.4 製品を追加するときの確認事項

- 「複数の現象があれば丸数字を振る」という運用(第3節)が、その製品の修理データでも同じか。
- その製品で、ユーザ起因とみなす環境要因は何か。
- 全コードの responsibility(第15.2節と同じ手順で、案を作ってユーザが決める)。
- 接続機器要因コードとサービスコードを用意すること。

### 16.5 想定していない製品への対応【確定】

- 今は想定していない製品も、YAML に製品セクションを足すだけで対応できるようにする。
- そのため、製品ごとに違いそうな部分はコードに書き込まず、すべて YAML の設定にする。

| 項目 | 設定の仕方 |
|---|---|
| 製品の識別子・表示名 | 製品セクションに書く |
| コードの接頭文字 | 製品セクションごとに決める(固定の割り当ては作らない) |
| 故障コード一式 | responsibility を含めて製品ごとに持つ |
| 環境要因の一覧・ユーザ起因の判定基準 | 共通の既定値(落下・水没など)を持たせ、製品ごとに追加・上書きできるようにする |
| 番号の付け方 | 既定は丸数字。運用が違う製品が出てきたら製品ごとに変えられるようにする |

- **YAML 読み込み時の自動チェック**(設定漏れの防止)
  - 必須コードがそろっているか(接続機器要因、サービスコード、その他、判定不能)
  - 全コードに responsibility が設定されているか
  - 接頭文字がほかの製品と重複していないか
- **新製品用のひな形と手順書を用意する**
  - 運用: ひな形をコピーして中身を埋め、自動チェックが通れば使える状態になる。
- **対応できない場合**: 修理データの入力の形そのものが違う製品(例: ユーザコメントと修理者コメントに分かれていない)は、YAML だけでは対応できず Python 側の修正が必要。
  - 入力の列が同じ(修理ID・製品種別・ユーザコメント・修理者コメント・内部コメント)なら、YAML だけで対応できる見込み。
